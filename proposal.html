CRM v3 Architecture Proposal

Restructuring our data model to serve two outreach tracks without recreating data.
CRM + HubSpot as centre of truth. Maximum reuse. Zero clones. Compliance-ready with full resilience layer.

+13 new tables −3 deprecated 8 tables enhanced 24 hardening fixes SQLite local → Postgres-ready
Why We're Changing
🔴 Problem 1 — Data Clones
company is a free text field on every contact. BMW appears 47 times. No account-level view. Can't say "all contacts at BMW" without a messy search.
✅ Fix — companies table with domain dedup
One row per company. All contacts reference it via company_id. Account intelligence stored once. All views derived from it.
🔴 Problem 2 — Split Status Systems
outreach.status and campaign_recipients.reply_status are separate and can drift. A campaign can mark someone "Sent" while the contact still shows "Pending".
✅ Fix — Campaign sends write back to outreach
One status state machine. Campaign sends trigger outreach.status update automatically. Single source of truth.
🔴 Problem 3 — No Track Separation
No way to tell if a contact came from a cold discovery batch or an organic intro. Can't segment reporting, filter by campaign eligibility, or track approval rates.
✅ Fix — entry_source + batch_id on persons
entry_source = cold | organic | inbound | referral. Every cold contact is linked to a discovery_batches row. Cohort analysis enabled.
🔴 Problem 4 — Nikhil Review Has No Home
Approval decisions from Nikhil's swipe review are not stored anywhere in the CRM. After the review, there's no data trail. Can't filter "show me only contacts Nikhil approved".
✅ Fix — contact_reviews table
One row per review decision. reviewer, decision, notes, reviewed_at. Stored separately from persons — contact stays clean. Multiple reviewers supported.
🔴 Problem 5 — No Enrichment Failure Tracking
Enrichment runs silently. If an Apify job fails or returns no data, there's no record of the failure, no retry, and no way to know which contacts were never enriched. Silent failures are invisible until a campaign goes out with empty fields.
✅ Fix — enrichment_jobs queue with retry
Every enrichment attempt creates a row in enrichment_jobs with status, error, next_retry_at. Exponential backoff. Failed jobs are visible and retryable. No more silent enrichment gaps.
🔴 Problem 6 — Email Sends Not Idempotent
If the scheduler crashes mid-send and retries, the same email can go out twice. campaign_recipients has no uniqueness constraint on the provider message ID, so there's no way to detect a double-send after the fact.
✅ Fix — provider_message_id UNIQUE + status on campaign_recipients
Adds provider_message_id UNIQUE, status, sent_at, last_error, attempt_count. The UNIQUE constraint prevents inserting a duplicate send record. Retries are safe — the constraint catches duplicates before the email goes out again.
🔴 Problem 7 — No Compliance Suppression
There is no mechanism to prevent sending email to someone who has unsubscribed, bounced permanently, or requested removal. Every send just goes through. This is a compliance risk and a deliverability risk.
✅ Fix — suppressions table checked before every send
New suppressions(email, reason, suppressed_at) table. The campaign engine checks this before queuing any recipient. Suppressed addresses never reach the scheduler — blocked at the pre-queue stage.
🔴 Problem 8 — Tags Are CSV Blobs
The tags TEXT column on persons stores comma-separated strings. Can't query by tag without LIKE hacks. No normalization — "robotics" and "Robotics" are different. No way to list all tags or count contacts per tag.
✅ Fix — tags + contact_tags normalized tables
New tags(name NOCASE UNIQUE) registry and contact_tags(person_id, tag_id) junction. Case-insensitive dedup enforced at DB level. Full tag analytics: count contacts per tag, filter by tag, bulk re-tag. Old TEXT column removed — no dual-write.

Hosting Strategy

📁 Now — SQLite Local

Single file database with WAL mode already enabled. Fast, zero infra, good for single user. Keep this for development and solo use. Backups auto-run to OneDrive on app close via backup_db() in closeEvent.

☁ Next — Postgres on Supabase (free)

Same schema, SQLAlchemy abstraction layer. Shared access for Vatsal + Nikhil. Always-on. No laptop dependency. One migration step — no query rewrites needed.

🔌 Add-on Pattern

Every new feature follows: new table with FK → contacts, new _migrate() block, new interaction rows for events. No schema rewrites, just additive growth.

🔄 HubSpot Sync Rule

Push to HubSpot only when outreach_status = Meeting Set. Keeps HS pipeline clean — no junk prospects, only real deals.
