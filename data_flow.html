CynLr CRM v2 — Two-Track Outreach Architecture

Cold Outreach (batch, AI-driven)  ·  Organic (manual, relationship-first)  ·  Both converge at Deal stage

v2 Architecture — Under Development
⬡ Design Thesis — Why Two Tracks?
Most CRM failures happen at the boundary between relationship and pipeline. A warm intro from Nikhil and a scraped LinkedIn profile are not the same object — but a flat schema treats them identically once imported. This architecture makes the entry condition a permanent, queryable fact.
Attribution Permanence
Six months from now when a deal closes, you can answer "was this cold outreach or organic?" without guessing. entry_source + origin_context are written once at import and never change. No relying on memory.
Clean HubSpot Pipeline
1,607+ contacts in local CRM. HubSpot sees only the ones with a real deal. By syncing at Meeting Set — not at import — every HubSpot metric is signal, not noise from batch imports that never converted.
One Infrastructure, Two Modes
Organic contacts never touch the campaign engine. Cold contacts get no ad-hoc nurture notes mixed in. But both use the same activity_log, same deal pipeline, same HS sync. One codebase, zero duplication.
The convergence insight: Meeting Set is the right merge point because deals are deals regardless of origin. The entry path matters for measurement (what's generating ROI?) — not for execution (what do we do next?). Collapsing both tracks at this point means zero special-case code after Meeting Set.

⬡ Convergence — Where Both Tracks Meet
Both tracks share the same deal pipeline from Meeting Set onward. HubSpot owns pipeline tracking.

Cold Track reaches this via

Reply to campaign email → Inbound activity logged
outreach_status → Replied → Meeting Set
Deal created → hs_sync_map row → HubSpot push

Organic Track reaches this via

Ongoing conversation signals real interest
outreach_status → Meeting Set (stage O4)
Deal created → hs_sync_map row → HubSpot push (stage O5)

5

↑ Migration Path — Current Schema → Target
All phases are additive. No existing data is deleted or overwritten. SQLite WAL mode stays on throughout.
P0
Backup DB
Copy crm.db to crm_backup_YYYYMMDD.db before touching anything. One command, 2 seconds.
Zero risk
P1
Add new tables
Add _init_companies(), _init_deals(), _init_activity_log(), _init_discovery_batches(), _init_contact_reviews(), _init_hs_sync_map(), _init_message_templates() to _migrate(). Additive — zero risk to existing data.
Additive
P2
Add columns to persons
ALTER TABLE contacts ADD COLUMN company_id INTEGER, entry_source TEXT, origin_context TEXT, batch_id INTEGER via existing _migrate() pattern. Old company TEXT column stays (SQLite can't drop; legacy reads still work).
Additive
P3
Backfill companies
One-time script: SELECT DISTINCT company FROM contacts WHERE company IS NOT NULL → INSERT INTO companies (name). Then UPDATE contacts SET company_id = companies.id WHERE contacts.company = companies.name. ~1,607 rows, runs in <1s.
Low risk
P4
Update _CONTACT_JOIN
Add LEFT JOIN companies ON companies.id = contacts.company_id to _CONTACT_JOIN. All existing queries (get_all_contacts, search, filter) instantly get company.name, company.industry, company.icp_fit for free. 3 lines.
Low risk
P5
Migrate activity data
One-time script migrates notes → activity_log (channel=note, direction=internal), messages → activity_log (channel=email, direction=outbound), activities → activity_log (channel=note, direction=internal). Old tables kept read-only — no DELETE. New writes go to activity_log only.
Medium — test first
P6
Update write paths
Replace add_note(), add_message(), add_activity() callers with add_interaction(). Update 14 MCP tools. Update Obsidian vault generator. Update campaign engine. Callers are all internal — no external API surface to break.
Low risk
P7
Status sync trigger
In set_status(): when status = Meeting Set, automatically create hs_sync_map rows + queue HubSpot push. campaign_recipients.reply_status drives outreach_status — one source of truth. 20 lines in set_status().
Zero risk
Do not skip P0. With 1,607 real contacts on a single SQLite file, one bad migration script = everything gone. Backup first, always.
